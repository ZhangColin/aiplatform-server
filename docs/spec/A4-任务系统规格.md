## 0. 总则

- **已继承不再重议**：任务五要素（内容/执行方/状态/确认模式/类型）与状态机骨架；Bug 字段与三态；确认模式 = 任务类型属性（v1 只有测试 = 人工确认），不做运行时覆盖；指派与领取分离，v1 只做指派；TaskCompleted 走**应用事件**（A1 修订）；转任务 → TaskCompleted → 复用会话续跑全链路随本票实例化（A1 §3，验收口径照 A1 §5）；「修复」走 dev 工作区智能体任务不进任务系统；任务/Bug 项目级、与过程正交（期后修复不锁，A3 缝③）。
- **本票新决策**四块：Bug 入库时点（§3）、修复编排粒度与循环（§4）、SSE 与可见性（§6/§7）、待办谓词澄清（§7）。

## 1. BC 与表

- 新 BC **`business.task`**（B0 §1 修订：从远期 BC 挪入 business 分区），错误码前缀 **`TASK_`**（ADR-0001 已预留位）。
- 表 **`tsk_tasks`**：`id` PK · `project_id` · `type`（v1 单值 TEST）· `title` · `content` · `assignee_account_id`（v1 指派必填）· `status` · `wait_id?`（转任务来源的不透明引用，可空，A1 §3）· `submitted_payload` jsonb?（已提交载荷暂存，§3）· `reject_reason?` · `rejected_at?`（重新提交时清空，TASK_REJECTED 待办判定用）· `confirmed_at?` · 审计字段。
  - **确认模式不落列**：由 type 推导（类型定义 = 代码概念，TEST → 人工确认）；自动确认类型是将来加 type 时的映射扩展。
- 表 **`tsk_bugs`**：`id` PK · `project_id` · `source_task_id`（来源测试任务）· `title` · `description` · `repro_steps` · `severity`（枚举档位实现票定名）· `attachments` jsonb?（URL 数组，**v1 留缝无上传通道**）· `status`（OPEN 待修复 / FIXED 已修复 / VERIFIED 复测通过）· `fix_run_id?` · `fix_note?`（修复 run 最终消息，「未重现」等结论如实记此）· `closed_reason?`（手工关闭理由）· 审计字段。

## 2. 任务状态机

`PUBLISHED 已发布 → IN_PROGRESS 执行中 → SUBMITTED 已提交 → CONFIRMED 已确认（终态）`；`CANCELLED 已取消（终态）`。

| 迁移 | 触发 | 守卫 |
|---|---|---|
| 已发布 → 执行中 | OPC `start` | 仅 assignee 本人 |
| 执行中 → 已提交 | OPC `submit`（载荷 §3） | 仅 assignee 本人；清空 rejected_at |
| 已提交 → 已确认 | dev `confirm` | Bug 入库 + 修复派发 + TaskCompleted（§3/§4/§8） |
| 已提交 → 执行中 | dev `reject`（reason 必填） | 记 rejected_at/reject_reason |
| 已发布/执行中 → 已取消 | dev `cancel` | **已提交不能取消只能驳回**（docs/11 原样） |

非法迁移 409 `TASK_`。

## 3. 提交与确认载荷（Bug 确认时入库）

- **首轮测试提交**载荷：`{ report: 测试报告文本, bugs: [{title, description, reproSteps, severity}] }`。
- **复测提交**载荷：`{ report, results: [{bugId, pass, note}] }`。
- 载荷暂存 `tsk_tasks.submitted_payload`（jsonb），驳回重交覆盖；**`tsk_bugs` 在确认前不动**——驳回/取消路径天然干净。
- **确认时一个事务内批量落库/翻态**：
  - 首轮确认：bugs 清单落 `tsk_bugs`（OPEN）→ AFTER_COMMIT 自动触发修复派发（§4）；
  - 复测确认：`pass=true` → VERIFIED；`pass=false` → 退回 OPEN → AFTER_COMMIT 自动再派发修复。
- **空 Bug 清单允许**（测试全过）：确认后无修复派发、RETEST_READY 不亮；无 OPEN Bug → G3 直接就绪，开发平台亮「开发完成确认」。

## 4. 修复循环编排（逐 Bug 一 run 一新会话）

**循环全貌**：dev 建测试任务（指派 OPC）→ OPC start → 执行 → submit（报告 + Bug 清单）→ dev confirm（Bug 入库 OPEN）→ **自动派发修复链** → 链完 RETEST_READY 亮 → dev 发复测任务 → OPC 复测提交（逐条结果）→ dev confirm（VERIFIED / 退回 OPEN 自动再派发）→ 循环至全 VERIFIED ∧ 无 OPEN Bug → G3 就绪。

- **粒度 = 逐 Bug 一 run 一新会话**（`sessionId=null`；不相关的 Bug 不共享上下文，docs/11「逐条修复」原文）。prompt = Bug 标题/描述/复现步骤 + 修复指令。
- **串行链**：同项目同时至多一个修复 run（同工作区并发互踩文件/git）；编排持 sink 收终态：正常 finish → 该 Bug 翻 **FIXED（乐观翻转）** + 记 `fix_run_id`/`fix_note` → 派下一条；error/timeout → 留 OPEN + `fix_run_id` 清回 NULL（日志留 runId）→ **失败不阻塞链**，该 Bug 回可派发池待下次派发。真伪由复测裁决——三态里复测本就是兜底。
- **派发幂等**：`dispatchFixes(projectId)` 只派 `OPEN ∧ fix_run_id IS NULL` 的 Bug；in-flight 判定 = 存在 `fix_run_id 非空 ∧ OPEN`。触发点三个：①首轮确认 ②复测确认（有退回时）③ dev 手动端点 `POST …/bugs/dispatch-fixes`。
- **重启恢复（从简，不建 campaign 表，#36 收口孤儿宽限）**：链是进程内 sink 回调，底座无 run 状态落库（B0 事实）查不到终态。「`fix_run_id 非空 ∧ OPEN` = 链必已死」只对本进程成立——共享库多实例下他实例启动扫描清走在飞标记即「终态守卫被拒 → 同一 Bug 修两次」（#30 冒烟 §7-② 实录）。故：启动扫描只回收**宽限外**的陈旧标记（标记落库时间超出引擎超时 `app.agent.timeout-minutes` + 5 分松弛——run 生命周期上界，两引擎同界），日志后置 NULL 回可派发池；宽限内的新鲜标记跳过（疑似他实例在飞 run）。重启后死链残留的新鲜标记无人收终态，由链前进步（触发点/终态续查）在宽限期满后回收续链——不留「卡 OPEN∧标记非空空转」的缝。重跑一次修复 = 无害冗余。持久化编排设施（campaign 表/重试策略/失败告警）等真痛再加（§10）。
- **bogus Bug**：dev 手工关闭 `POST …/bugs/{bugId}/close`（reason 必填）→ VERIFIED + `closed_reason`。**不加第四态**：复测通过是唯一关闭态，手工关闭是其带理由的别名动作，G3 谓词不变。
- **落码归属**：修复编排链在 `business.task` application 层，经 `business.project` 的工作区任务下发端口下发（阶段计数 / SSE 桥接 / UsageContext 全继承片 5 编排）；systemPrompt 取 DEV 类 preset，计量 dims `role=FIX` 区分。期 CLOSED 后的修复 run 无期可挂，跳过阶段计数（工具正交）。
- **风险注记**：修复链与开发平台手动下任务的工作区互斥 v1 **不做硬锁**（UI 可见 run 进行中，开发平台自律）；痛则成票（地图雾）。

## 5. 期联动（A3 缝落地）

- **advance 守卫**：创建测试任务时若期当前 stage=开发 → advance（开发→测试的唯一触发）；stage=测试（复测场景）或期 CLOSED（期后修复）→ 不动。
- **`hasOpenBugs(projectId)` 查询端口**（task BC 提供、project 消费）：G3 业务谓词（approve 前校验）与 G3 门就绪派生共用；**open = status ≠ VERIFIED**。
- 修复 run 经片 5 编排自动计入当前阶段计数——测试段 `minTasks=1` 由此凑上（测试段的 agent 任务即修复 run）。
- 需求端「测试中」= 期 stage 投影，零新增机制（A3 已覆盖）。

## 6. API 与 SSE

| 端点 | 视角 | 说明 |
|---|---|---|
| `POST /api/projects/{id}/tasks` | dev | 建测试任务（type=TEST 固定；assignee 必填）；处 advance 守卫（§5） |
| `GET /api/projects/{id}/tasks` | dev | 项目任务列表全量（含状态/驳回理由） |
| `GET /api/tasks` | opc | assignee=me 跨项目；卡片含最小项目上下文（§7） |
| `GET /api/tasks/{taskId}` | opc/dev | opc 校验 assignee=me |
| `POST /api/tasks/{taskId}/start` | opc | 已发布 → 执行中 |
| `POST /api/tasks/{taskId}/submit` | opc | → 已提交，载荷 §3 |
| `POST /api/tasks/{taskId}/confirm` | dev | → 已确认；Bug 入库/翻态 + 修复派发 + TaskCompleted |
| `POST /api/tasks/{taskId}/reject` | dev | reason 必填 |
| `POST /api/tasks/{taskId}/cancel` | dev | 仅已发布/执行中 |
| `GET /api/projects/{id}/bugs` | dev | 列表 + 状态/fix_run_id/fix_note/closed_reason |
| `POST /api/projects/{id}/bugs/dispatch-fixes` | dev | 幂等手动（重）派发 |
| `POST /api/projects/{id}/bugs/{bugId}/close` | dev | reason 必填；→ VERIFIED |
| `GET /api/accounts` | dev | business.identity 加；指派下拉 |

- **SSE 新增 `task-updated`**（平台通知通道，进 [SSE 清单](SSE事件清单.md) 治理）：payload `projectId` `taskId` `status`，任务状态每次迁移发一条；Bug 状态不单独发（随任务与 REST）。任务平台布局挂通知通道收 `task-updated` 过滤自己的任务即重拉——「事件让 UI 活，正确性走 REST」（ADR-0001）。

## 7. 可见性与待办接线（A2 落地）

- **opc 视图按 `assignee = 当前账号` 过滤**（资源归属谓词，非角色挡端点——A2 两谓词模型的归属半边；v1 两个真实账号登录自然成立）；dev 全量；需求端零新增。
- **最小项目上下文**：项目名 + 预览地址必带；PRD 全文复用片 5 既有产物读取，无现成读取则 v1 不带（留缝）。
- **四型待办源**（A2 §4 接线落地）：

| type | 源（澄清后） |
|---|---|
| `TASK_SUBMITTED` | 存在 status=SUBMITTED 的任务 |
| `RETEST_READY` | 存在 FIXED Bug ∧ 无进行中测试任务（PUBLISHED/IN_PROGRESS/SUBMITTED）∧ 无 in-flight 修复 |
| `NEW_TASK` | assignee=me ∧ PUBLISHED |
| `TASK_REJECTED` | assignee=me ∧ IN_PROGRESS ∧ rejected_at 非空（重新提交即离开） |

（A2 原文「Bug 全闭环 ∧ 无未关闭复测任务」措辞已修正，连带修订。）

## 8. TaskCompleted 与转任务回填（A1 §3 实例化）

- 载荷：`taskId` · `type` · `assignee` · `completedAt` · `waitId?` · `summary`（测试报告文本 + Bug 清单 / 复测结果）。
- **确认时发**（AFTER_COMMIT，cartisan PUBLISHER 端口）；驳回/取消不发。幂等以状态机守门（CONFIRMED 才发）。
- project 应用层监听（唯一流程反应者）：`waitId` 非空 → `runTask` 复用原 sessionId、prompt = summary（续跑 = 给会话的新消息）；会话/环境已亡 → 记日志跳过不抛（A1 §3.2）。
- 结算钩子 v1 不碰钱、无其他订阅方（发布端就位原则，A1 同款）。

## 9. 对 A5 的缝

- 沉淀写挂钩 = **任务确认时刻**（测试报告 + Bug 清单入库 `knw_*`，demo `indexArtifacts` 语义随 A5 定）；本票保证素材落点：`submitted_payload` + `tsk_bugs`。（A5 已定稿：TEST_REPORT / BUG 两类，AFTER_COMMIT 摄取、幂等 by (kind, source_ref)，见 [A5 规格](A5-知识沉淀规格.md) §1。）
- 复测通过记录（VERIFIED 时刻 + closed_reason）= 交付审计与纪要素材。
